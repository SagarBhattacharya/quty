Quty Documentation

Overview

Quty is a multithreaded, in-memory cache daemon written in Rust. It provides sub-millisecond key-value operations, deterministic payload memory budgeting, and single-shard atomic batch transactions with guaranteed rollback invariants.

Core Capabilities

  • Partitioned Key-Space: Power-of-two sharding with independent parking_lot::RwLock instances reduces contention by isolating most operations to individual shards.
  • Payload-Byte Budgeting: Accounts for key and value bytes, excluding data-structure and allocator overhead. The budget is not a process-RSS limit.
  • Sampled LRU Eviction: Uses a dense key index for candidate sampling without scanning the entire hash map.
  • Atomic Batch Transactions: Single-shard batches use an undo log to restore prior state when an operation fails.
  • Binary Wire Protocol: A fixed 20-byte header supports incremental decoding and bounded request and response payloads.

Architecture & Design

quty decouples storage partitioning, mutation execution, and networking into clean workspace boundaries.

Architectural Principles

  1. Shard-Scoped Synchronization: Most operations synchronize on the shard they access. Operations such as RESET acquire all shard locks in a consistent order.

  2. Payload-Byte Budgeting: Memory accounting tracks key and value byte lengths. It excludes hash-table/index capacity, entry metadata, allocator overhead, and other process allocations; it is not a strict RSS ceiling. The budget is divided among shards.

  3. Transactional Safety: Single-shard batches use inverse mutations to restore prior state when a transaction fails.

Binary Wire Protocol Specification (v1)

This document defines the wire specification for the Quty protocol (v1). Any compliant client or driver implementation in any language must adhere to the framing, field widths, endianness, and error invariants defined here.

1. Network Transport Invariants

  • Transport Layer: TCP stream. Sockets MUST configure TCP_NODELAY = 1 to disable Nagle’s algorithm.
  • Byte Ordering: All multi-byte numerical fields (16-bit, 32-bit, and 64-bit) MUST be encoded in Big-Endian (Network Byte Order).
  • Framing Invariant: Every network message begins with a fixed 20-byte header. The header explicitly declares the payload byte length (payload_len), allowing decoders to determine frame boundaries before consuming variable-length payload bytes.

2. Frame and Payload Limits

  • Every request and response begins with a 20-byte header.
  • A frame payload must not exceed 64 MiB.
  • A batch request or response array must contain no more than 64 operations or results.
  • Decoders validate complete headers before waiting for payload bodies.
  • Request flags must be zero.
  • Fixed-width response payloads must have their exact defined lengths.
  • Invalid lengths, malformed payloads, and unexpected trailing bytes are rejected.

6. Shard Partitioning & Transaction Invariants

6.1 Prefix Routing

All keys are routed to a shard using the string prefix preceding the first colon (:).

  • session:user_123 and session:user_456 map to the same partition.
  • If no colon exists (e.g., counter), the entire key string is hashed.

6.2 Batch Single-Shard Constraint

Atomic batches (0x02) MUST NOT cross shard boundaries.

If a batch contains keys that resolve to different shards, the server MUST abort before executing any mutations and return status code 0x32 (CrossShardViolation).

6.3 Rollback Semantics

If any operation in a batch produces a hard error, such as StorageFull or KeyExists, all previous mutations in that batch MUST be rolled back immediately.

The server MUST return status code 0x34 (BatchShortCircuited) with a BatchErr payload identifying the failed operation and its failure status code.

Server Engine & Storage Architecture (quty-server)

This document details the internal design, concurrency guarantees, memory allocation, and transaction pipeline of the quty-server caching daemon.

1. Concurrency & Partitioning Architecture

To eliminate global mutex bottlenecks under high read/write concurrency, quty-server splits its keyspace into (N) independent, power-of-two partition shards.

Architecture Overview

                              Incoming Request
                                     |
                                     v
                     Hash Partition: ahash(routing_key) & (N - 1)
                                     |
         +---------------------------+---------------------------+
         |                           |                           |
         v                           v                           v
  Shard Lock [0]              Shard Lock [1]              Shard Lock [N-1]
+-----------------+         +-----------------+         +-----------------+
| parking_lot     |         | parking_lot     |         | parking_lot     |
| RwLock<Shard>   |         | RwLock<Shard>   |         | RwLock<Shard>   |
+--------+--------+         +--------+--------+         +--------+--------+
         |                           |                           |
         v                           v                           v
+-----------------+         +-----------------+         +-----------------+
|  ShardStorage   |         |  ShardStorage   |         |  ShardStorage   |
|  - AHashMap     |         |  - AHashMap     |         |  - AHashMap     |
|  - Vec<Box<str>>|         |  - Vec<Box<str>>|         |  - Vec<Box<str>>|
|  - Memory Bytes |         |  - Memory Bytes |         |  - Memory Bytes |
+-----------------+         +-----------------+         +-----------------+

Partition Properties

  • Bitwise Masking: When num_shards is a power of two, routing resolves via hash & (num_shards - 1), avoiding CPU division instructions.
  • Shared Read Concurrency: Read operations (GET, EXISTS, TTL) acquire a shared read lock using shard.read().
  • Atomic Clock Updates Under Shared Lock: Recency tracking is managed through Entry.last_accessed: AtomicU32. A GET request updates the LRU clock using relaxed atomic stores without acquiring an exclusive write lock.

2. Memory Accounting & Sampled LRU Eviction

Memory management enforces deterministic bounds calculated strictly from key length and value payload length.

Data Structures (Shard)

Each shard maintains two synchronized data structures:

  1. entries: AHashMap<Box<str>, Entry> — the primary key-value mapping, storing payload slices, optional deadlines, and clock metadata.
  2. keys: Vec<Box<str>> — a dense vector containing active keys for uniform candidate sampling.

Data Structure Relationship

Vec<Box<str>>:     [ "user:1", "user:2", "user:3", ... ]
                                ^
                                |
                                | key_index: 1
                                |
AHashMap:          "user:2" => Entry {
                                value,
                                expires_at,
                                last_accessed,
                                key_index: 1
                            }

O(1) Swap-Remove Invariant

When an entry is removed from the shard:

  1. The entry is removed from entries.
  2. The key at index entry.key_index is removed from keys via keys.swap_remove(idx).
  3. If an element from the tail of the vector is moved into the vacated position, its corresponding entry in entries has its key_index updated to idx.

This guarantees that candidate sampling remains O(1), without requiring bucket iteration or allowing tombstone leakage in the dense key vector.

Eviction Pipeline (LruPolicy)

  • Inline Headroom Eviction: When a write requires more memory than is available, LruPolicy::evict_headroom samples up to DEFAULT_SAMPLE_SIZE (5) keys, selects the one with the highest idle duration, and removes it. This repeats until the required headroom is reclaimed or the attempt limit is reached.
  • Self-Eviction Shield: Before checking headroom for an update to an existing key, the mutation pipeline invokes shard.touch(key, clock). This resets its idle duration, preventing an active key from evicting itself during an in-place update.
  • Background Maintenance Sweep: Every sweep_interval_ms, a background worker samples keys to reclaim expired TTL entries. If memory exceeds high_watermark, it evicts candidates in bursts of eviction_burst_limit until memory drops below low_watermark.

3. Transaction Execution & Rollback Pipeline

Batch operations execute atomically within a single shard using an inverse mutation log.

Transaction Flow

                  Batch Request [cmd0, cmd1, cmd2]
                                 |
                                 v
                   Verify Prefix Alignment (is_single_shard)
                                 |
                                 v
                    Acquire Shard Write Lock
                                 |
                                 v
                    Spawn RollbackGuard (RAII)
                                 |
                 +---------------+---------------+
                 |                               |
                 v                               v
          execute_mutation(op0)           execute_mutation(op1)
                 |                               |
                 v                               v
          Record UndoRecord                Record UndoRecord
          [UndoRecord::Restore]            [UndoRecord::Delete]
                 |                               |
                 +---------------+---------------+
                                 |
                                 v
                 Condition Failure on op2 (KeyExists)
                                 |
                                 v
                     Early Return: Status Abort
                                 |
                                 v
                     RollbackGuard Drops
                                 |
                                 v
                     Unroll Undo Stack (LIFO)
                     - Undo op1: Delete newly inserted key
                     - Undo op0: Restore displaced entry

Inverse Undo Actions (UndoRecord)

  • Delete { key }: Undoes a newly inserted key.
  • Restore { key, entry }: Restores an overwritten or deleted entry to its exact prior state.
  • RevertExpiry { key, previous_deadline }: Restores a previously configured expiration deadline.

Transaction Invariants

  1. Eviction Prohibition: Atomic batches execute with allow_inline_eviction = false. If a batch operation exceeds capacity, it fails immediately with StatusCode::StorageFull and triggers rollback rather than evicting existing keys.
  2. Panic Safety: If an unhandled panic occurs in a worker thread during batch processing, Rust’s stack unwinding executes RollbackGuard::drop(), ensuring that shard state and memory accounting remain consistent.

Signal Handling & Graceful Drain

  • Multi-Signal Detection: The runtime listens concurrently for SIGINT (Ctrl+C) and SIGTERM (container orchestrators).
  • Connection Draining: Upon receiving a shutdown signal, cancel_token.cancel() notifies all active connection loops.
  • TaskTracker Barrier: The server closes its listener, allows in-flight operations to finish writing responses, and waits up to shutdown_timeout_secs before forcing process exit.
  • Buffer Compaction: Connections reclaim excess buffer capacity when processing large payloads expands internal buffers beyond 1 MB.

5. Memory Accounting

Quty accounts for the byte lengths of keys and values. This is a payload-byte budget, not a strict process-memory ceiling. Hash-map buckets, dense-index storage, entry metadata, allocator overhead, and other process allocations are excluded.

The configured budget is divided among shards. A shard may reach its budget even when other shards have unused capacity.

Eviction Behavior

Before evicting entries to reclaim headroom, the eviction policy determines whether the selected candidates can free enough accounted bytes. If the capacity requirement cannot be satisfied, the operation fails without removing those candidates.

6. RESET Semantics

RESET acquires all shard write locks in ascending shard-index order, clears the shard contents, and resets hit, miss, and eviction counters. Uptime, total connections, and active-connection counts are preserved.

Client Driver & CLI Guide (quty-client)

This document details the architecture, design choices, error-handling semantics, and execution modes of quty-client.

1. Architectural Design

quty-client fulfills two architectural functions:

  1. Asynchronous Library Driver: A lightweight, non-blocking network client built on tokio and bytes for application integration.
  2. Operational Terminal Client (quty-cli): An interactive REPL and scriptable CLI tool for server administrators and DevOps workflows.

2. Network Loop & Invariant Safety

2.1 Monotonic Request Correlation

The client implements a strict request-response correlation check. For every command dispatched over the wire:

  1. An internal request_id_counter: u64 increments monotonically.
  2. The request ID is encoded into bytes 8..16 of the 20-byte header.
  3. Upon receiving a frame, the client verifies that the response request ID matches the expected request ID.
#![allow(unused)]
fn main() {
if response.header.request_id != expected_req_id {
    return Err(RequestCorrelationError);
}
}

This catches socket desynchronization, interleaving anomalies, or corrupted frames immediately.

2.2 Connection Poisoning Guard

Network protocols operating over raw TCP streams can become desynchronized if an I/O timeout, frame parsing error, or unexpected connection drop occurs mid-payload.

To eliminate subtle downstream data corruption, quty-client implements connection poisoning:

  • If Client::execute encounters an I/O error or decoding failure, self.is_poisoned is set to true.
  • Subsequent attempts to reuse the client instance immediately fail with io::ErrorKind::BrokenPipe.
  • Callers must establish a fresh TCP connection via Client::connect() rather than continuing on a potentially desynchronized byte stream.

This prevents the client from interpreting stale or incomplete response bytes as responses to subsequent requests.

2.3 Memory Capacity Compaction

When reading large values (up to 32 MB), the underlying read_buf: BytesMut grows to hold incoming frames. To prevent sustained memory bloat, Client monitors the buffer’s capacity after execution.

#![allow(unused)]
fn main() {
if self.read_buf.is_empty() && self.read_buf.capacity() > 1024 * 1024 {
    self.read_buf = BytesMut::with_capacity(64 * 1024);
}
}

Whenever the buffer is completely drained and its allocated capacity exceeds 1 MB, the client replaces the oversized buffer with a new buffer initialized with a baseline capacity of 64 KB.

3. Shell Automation & Exit Code Semantics

When running in one-off mode (for example, quty-cli -p 6379 GET key:1), the process exit status follows conventional systems-operation semantics.

Exit Code 0 — Success

  • Operational completions: StatusCode::Ok, StatusCode::Created, and StatusCode::NoContent.
  • Cache misses: StatusCode::KeyNotFound and StatusCode::KeyExpired.

A cache miss is treated as a successful query evaluation. This ensures shell scripts do not fail prematurely when querying optional keys.

Exit Code 1 — Failure

  • Network I/O failures, connection refusals, or timeouts.
  • Syntax and tokenization errors.
  • Hard engine errors, including:
    • PreconditionFailed
    • StorageFull (out-of-memory or capacity limit)
    • CrossShardViolation
    • BatchShortCircuited
    • Protocol violations

Scripting Example

#!/usr/bin/env bash
set -e

# Conditional execution: fails the script only if a real hard error occurs.
quty-cli -p 6379 SET user:100:active "true"

# Checking existence in automation.
STATUS=$(quty-cli -p 6379 EXISTS user:100:active)
echo "Query completed: $STATUS"

4. Interactive REPL Architecture

The interactive REPL is powered by rustyline and provides the following capabilities.

Command Persistence

Commands are saved to ~/.quty_history during execution and reloaded when the REPL starts.

Lexical Parser

The tokenizer supports whitespace-separated arguments alongside quoted string literals, allowing values to contain spaces.

Example:

SET user:100:profile "Alice Smith"

Cross-Shard Batch Guard

When parsing BATCH (...), quty-client validates is_single_shard() before serializing the request.

Cross-shard batches fail immediately in the client terminal with actionable guidance, without sending invalid traffic to the server.

This client-side validation complements the server’s own shard-boundary enforcement and avoids unnecessary network round trips for invalid batches.

3. Performance Analysis

3.1 Read and write throughput

Write-heavy workload

The SET workload reached approximately 2.34 million requests/s, with p50 latency of 18 µs and p99 latency of 57 µs.

Read-heavy workload

The GET workload reached approximately 2.09 million requests/s, with p50 latency of 21 µs and p99 latency of 64 µs.

These results are consistent with an architecture designed to reduce contention through independently locked storage shards. They do not, by themselves, isolate the contribution of sharding from the effects of pipelining, client concurrency, allocator behavior, or other implementation details.

Read recency tracking uses relaxed atomic updates through AtomicU32, allowing the relevant recency update to avoid requiring an exclusive lock solely for that update. This design choice may help reduce read-side contention.

3.2 Mixed and skewed workloads

The mixed workload reached approximately 2.03 million requests/s, with p99 latency of 65 µs.

The Zipfian-skew workload reached approximately 1.91 million requests/s, with p99 latency of 71 µs.

The lower throughput and higher tail latency under skew are consistent with increased contention when a disproportionate share of operations targets a smaller subset of keys. The results alone do not quantify how much of the difference is caused by shard contention versus other workload effects.

3.3 Pipeline depth and throughput

The unpipelined workload reached approximately 170,139 requests/s, compared with approximately 2.81 million requests/s at pipeline depth 32.

Pipelining amortizes per-request transport and syscall overhead across multiple requests. However, pipeline depth also changes the timing and batching characteristics of the workload, so the latency figures should not be interpreted as a direct comparison of isolated single-request response times under otherwise identical conditions.

These results do not independently establish that the server is memory-bandwidth-bound or has reached its maximum throughput.

3.4 Atomic batch commits and rollbacks

The batch workloads use three operations per batch for the commit scenario (SET, SET, GET) and deliberately trigger a failure on the final operation in the rollback scenario.

With three operations per committed batch, the commit result corresponds to approximately 2.53 million sub-operations/s, assuming all three operations are counted as one sub-operation each.

The rollback path uses a RollbackGuard and an undo stack backed by SmallVec<UndoRecord, 16>, intended to reduce allocation overhead for small transactions.

The observed rollback throughput is higher than commit throughput in this run. That does not establish that rollback is intrinsically faster or incurs no performance penalty: the workloads perform different amounts of work. Repeated trials and comparable transaction paths would be required to draw that conclusion.

The results apply to the tested single-shard batch model and should not be interpreted as evidence of cross-shard transaction support.

4. Reproducing the Benchmarks

4.1 Build and start the server

Build the optimized server:

cargo build --release -p quty-server

Start it with the benchmark configuration:

./target/release/quty-server \
    --bind 127.0.0.1:6379 \
    --shards 64 \
    --max-memory 1GB

Confirm that the server’s supported command-line arguments match the flags above before running the suite.

4.2 Run the benchmark suite

In another terminal, execute:

./quty-bench/scripts/run_benches.sh

The runner executes the configured workload scenarios and reports throughput and latency measurements.

For meaningful comparisons:

  • Use the same server build, machine, and configuration.
  • Keep concurrency, pipeline depth, key distribution, and payload sizes consistent.
  • Ensure the database reset and any prepopulation finish before measurement begins.
  • Run each scenario multiple times and compare medians across runs.
  • Record failures and incomplete runs rather than treating partial results as successful benchmarks.
  • Verify that latency percentiles represent per-request measurements rather than an aggregate pipeline duration divided by pipeline depth.

5. Limitations

These results should be interpreted with the following limitations in mind:

  1. Local-only testing: Loopback TCP does not represent remote network latency or network congestion.
  2. Hardware specificity: Results depend on the CPU, memory, operating system, runtime, allocator, and server configuration.
  3. Workload dependence: Key distribution, operation mix, pipeline depth, and concurrency materially affect results.
  4. Short measurement windows: Approximately 10 seconds per workload may not reveal long-running behavior, sustained memory pressure, or periodic latency spikes.
  5. Statistical uncertainty: A single reported result does not establish run-to-run variance or reproducibility.
  6. No universal comparison: These measurements cannot establish superiority over other cache engines without equivalent workloads, configurations, and measurement procedures.

6. Summary

The benchmark suite demonstrates high local request throughput for quty-server under concurrent, pipelined workloads. The highest measured throughput was approximately 2.81 million requests/s at pipeline depth 32. The read, write, and mixed workloads also exceeded two million requests/s in the reported runs.

Pipelining produced the largest observed throughput difference, while skewed access and batch execution provided additional information about the system’s behavior under different workload patterns.

These figures are local benchmark observations, not universal performance guarantees. Repeated trials, verified per-request latency measurements, and controlled comparisons are necessary for stronger performance claims.
